# 음량 버튼으로 앞·뒤 알 — 조사와 판정 (FR-38)

> 한 줄 요지: **지금의 Expo 관리형 구조 안에서는 Android 의 음량 버튼을 잡을 길이 없다.** Expo SDK 57 이 제공하는 모듈과 React Native 자체에는 하드웨어 음량 키를 앱에 알려 주는 통로가 없어, 붙이려면 네이티브 부품(모듈)을 새로 얹어야 한다. 부품을 얹는 것은 빌드 방식을 바꾸는 일이라 공방장의 승인이 필요하므로 이번에는 얹지 않았고, 붙을 자리만 `src/prayer/handsfree.ts` 에 주석으로 표시했다.

## 먼저 정해져 있던 것 둘

이 조사는 두 결정 위에서 했다.

1. **iOS 에서는 쓰지 않는다.** 애플은 음량 버튼을 음량 조절 외의 용도로 쓰는 앱을 심사에서 거절한다(앱스토어 심사 지침 2.5.9). 요구사항 문서 §11-3 이 이미 판정했고, 흔들기와 이어폰 버튼만 iOS 의 손 없이 조작이다.
2. **V1 검증 빌드에서는 Android 에서도 쓰지 않는다.** `decisions.md` 결정 큐 Q-06a — 검증 기간에 플랫폼별 동작 차이를 만들지 않고 네이티브 모듈 하나를 줄이기 위해, Android 음량 버튼은 08 검증 결과를 보고 M5(정식 출시)에서 판단한다.

그래서 이 문서가 답하는 질문은 "지금 붙일 것인가"가 아니라 **"붙이기로 정한다면 무엇이 필요한가"** 다. 그리고 하나 더 — 지금 공방장이 쓰는 것은 웹 빌드이고, **웹 브라우저는 어떤 방법으로도 기기의 음량 버튼을 앱에 알려 주지 않는다.** 웹에서는 이 기능을 확인할 수 없다.

## 무엇을 살폈나

`package.json` 의 의존성과 `app.json` 의 플러그인 목록을 기준으로, 이 앱이 이미 갖고 있는 부품 안에서 음량 키를 받을 수 있는지 봤다.

| 살핀 것 | 결과 |
|---|---|
| `expo-sensors` (지금 흔들기에 쓴다) | 가속도·자이로·기압 같은 **센서**만 있다. 키 입력은 없다 |
| `expo-speech` | 낭송의 **음량을 정하는** 옵션(`volume`)은 있지만, 기기의 음량 버튼이 눌렸다는 것을 알려 주지는 않는다 |
| `expo-keep-awake` · `expo-router` · `expo-image` · `expo-font` 등 나머지 Expo 모듈 | 음량 키와 무관하다 |
| React Native 자체 | Android 의 하드웨어 키 중 앱에 알려 주는 것은 **뒤로 가기(`BackHandler`) 하나**다. 음량 위·아래 키는 앱에 전달되지 않고 시스템이 음량을 바꾼다 |
| 브라우저(웹 빌드) | 음량 키는 브라우저에 닿지 않는다. 미디어 세션(이어폰 단추가 오는 길)에도 음량 키는 없다 |

결론: **지금 갖고 있는 부품으로는 안 된다.** 이 앱의 손 없이 조작 셋 중 흔들기와 이어폰 단추는 이미 있는 부품(센서 · 미디어 세션)으로 되지만, 음량 버튼만은 그렇지 않다.

## 붙이려면 무엇이 필요한가

Android 에서 음량 키를 앱이 받으려면 **화면(`Activity`)이 키 입력을 가로채는 네이티브 코드**가 있어야 한다. 그 코드를 이 저장소에 들이는 길은 둘이고, 둘 다 네이티브 부품이다.

| 길 | 무엇인가 | 대가 |
|---|---|---|
| 키 이벤트를 앱에 전달하는 부품 (예: `react-native-keyevent` 계열) | Android 의 `onKeyDown` 을 가로채 자바스크립트로 넘긴다. 음량 키를 우리가 받는 대신 **시스템의 음량 조절을 막을 수도 있다** | `MainActivity` 를 고쳐야 한다. Expo 관리형 구조에서는 그 수정을 자동으로 넣어 주는 설정 플러그인(config plugin)을 함께 써야 하고, 플러그인이 없는 부품이면 우리가 써야 한다 |
| 시스템 음량의 변화를 지켜보는 부품 (예: `react-native-volume-manager` 계열) | 음량이 바뀌었다는 사실을 받아 "위로 갔으면 다음 알, 아래로 갔으면 앞 알"로 해석한다 | 음량이 **실제로 바뀐다.** 기도 중에 음량 버튼을 누를 때마다 낭송 소리가 커졌다 작아졌다 하므로, 눌린 뒤 원래 값으로 되돌리는 코드가 함께 필요하고, 그래도 소리가 튄다 |

어느 길이든 공통으로 따라오는 것이 있다.

- **네이티브 빌드(EAS Build)를 거쳐야 동작한다.** 지금 공방장이 확인하는 웹 빌드에서는 붙여도 아무 일이 일어나지 않고, 실기기 Android 빌드를 만들어야 처음 확인할 수 있다.
- **iOS 와 웹에서는 코드가 있어도 켜지지 않아야 한다.** `Platform.OS === 'android'` 안에서만 부르고, 부품 자체도 iOS 심사 메모("음량 버튼 미사용", 개발 계획 §M5 심사 표)와 어긋나지 않게 iOS 에서는 아무 일도 하지 않게 둔다.
- **음량 버튼을 조작에 쓰면 사용자는 기도 중에 음량을 바꿀 수 없다.** 이것은 부품이 아니라 제품의 선택이고, 설정의 "손 없이 조작"이 켜져 있을 때만 그렇게 되게 해야 한다.

## 판정

**이번에는 붙이지 않는다.** 이유는 셋이다.

1. 있는 부품으로는 안 되고, 부품을 얹는 것은 빌드 방식을 바꾸는 일이라(결정 3 의 스택 위에 네이티브 모듈을 더하는 것) 공방장의 승인이 필요하다.
2. 결정 큐 Q-06a 가 V1 검증 빌드에서는 양 플랫폼 모두 음량 버튼을 쓰지 않기로 이미 정해 두었다.
3. 웹 빌드에서는 어차피 확인할 수 없어, 지금 붙여도 "동작한다"를 증명할 길이 없다.

붙을 자리는 `src/prayer/handsfree.ts` 의 `useRemoteCommands` 아래에 주석으로 표시해 두었다. 부품이 정해지면 그 자리에 `useVolumeButtons(enabled, { onNext, onPrevious })` 같은 갈고리 하나가 들어오고, `usePrayerSession.ts` 의 손 없이 조작 줄에서 흔들기·이어폰과 나란히 불리게 된다.

## 공방장이 정할 것 — M5 에서

Q-06a 가 M5 로 미룬 판단이 이것이다. 그때 답할 질문은 기술이 아니라 이 둘이다.

- **Android 사용자에게 음량 버튼이 흔들기·이어폰 단추 위에 더해질 만큼 값어치가 있나.** 08 검증에서 Android 참가자가 흔들기만으로 다섯 단을 끝까지 갔다면 필요가 낮고, "손에 든 채 버튼을 누르고 싶다"는 말이 나왔다면 필요가 높다.
- **그 값어치가 네이티브 부품 하나(빌드 복잡도 · 유지 비용 · 음량을 못 바꾸게 되는 대가)를 치를 만한가.**

답이 "그렇다"면 위 표의 첫 길(키 이벤트 부품)을 권한다. 음량이 실제로 튀지 않기 때문이다.
