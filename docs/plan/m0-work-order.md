# M0 작업 지시서 — 바닥이 실제로 선다는 것을 증명한다

> 한 줄 요지: **M0에서 만드는 것은 앱이 아니라 바닥이다.** Expo 프로젝트를 세우고, `spec/`의 기도 규칙과 `docs/design/v5/`의 화면 값을 코드로 옮기고, 그것들이 실제로 동작한다는 것을 **웹 빌드에 뜬 로그인 화면 한 장**으로 증명한다. 화면 열 중 아홉은 M1·M2·M3의 일이다.

받는 사람 KimDeveloper · 쓴 사람 KimPM · 2026-09-08 · 브랜치 `claude/my-rosary-app-development-pmbcy9`

**먼저 읽을 것 셋.** `decisions.md`(결정 1·2·3과 결정 큐 Q-13·14·15) · `docs/plan/development-plan.md` §6-3(마일스톤 전체와 v5 값의 소재) · `docs/design/v5/README.md`(시안 정본의 구조). 이 지시서는 그 셋을 대신하지 않고, M0에서 무엇을 어떤 순서로 만들고 무엇으로 통과 판정을 받는지만 정한다.

## 1. 먼저 알아야 할 환경의 사실 — 여기서 무엇이 가능하고 무엇이 불가능한가

착수 전에 이 환경을 직접 재서 확인한 것이다. 이 사실들이 M0의 범위를 그대로 결정했으므로 가장 먼저 적는다.

| 확인한 것 | 결과 | 이것이 M0에 뜻하는 바 |
|---|---|---|
| Node 버전 | **v22.22.2** | Expo SDK 최신판이 요구하는 버전을 넘긴다. 별도 설치가 필요 없다 |
| npm 버전 | **10.9.7** | 그대로 쓴다 |
| npm 레지스트리 접근 | **가능** (ping 통과) | 패키지 설치가 된다 |
| `expo` 패키지 최신 버전 | **57.0.21** 조회됨 | 프로젝트 생성이 실제로 가능하다는 뜻이다 |
| 운영체제 | **리눅스 컨테이너. 맥이 없다** | **iOS 빌드가 이 환경에서 원천적으로 불가능하다.** 문법이나 설정의 문제가 아니라 애플이 iOS 빌드에 맥을 요구하기 때문이다 |
| 클라우드 iOS 빌드(EAS Build)의 조건 | Expo 계정 + Apple Developer 계정 | 둘 다 **사람이 만들어야 하는 계정**이라 이번 턴에 없다. §8의 부탁으로 올렸다 |

**여기서 곧바로 나오는 결론.** M0에서 **이 환경이 스스로 검증할 수 있는 것**은 넷이다 — 프로젝트가 설치되는 것, 타입 검사와 단위 테스트가 통과하는 것, **웹 빌드(`expo export --platform web`)가 성공하는 것**, 그리고 Playwright로 그 웹 빌드를 띄워 화면이 실제로 뜨는 것까지다. **네이티브 빌드(iOS·Android)는 M0의 통과 조건이 아니다.** 설정 파일(`app.json`·`eas.json`)을 갖춰 두고 "계정 연결 뒤 실행" 상태로 남긴다.

이것을 얼버무리지 않는 이유가 있다. 2026-09-05 판 계획은 M0의 노출 증명을 "클라우드에서 iOS·Android 빈 앱 빌드 성공 로그 + TestFlight 배포"로 적어 두었는데, **그 조건은 이 환경에서 사람의 계정 없이는 영원히 충족되지 않는다.** 충족 불가능한 조건을 걸어 두면 M0가 끝나지 않거나, 끝나지 않았는데 끝났다고 말하게 된다. 그래서 M0의 조건을 이 환경이 실제로 잴 수 있는 것으로 다시 잡고, 못 하는 것은 §7에 이름을 붙여 남긴다.

## 2. M0의 목적 — 화면을 만드는 일이 아니다

M0가 답하려는 질문은 하나다. **"우리가 고른 바닥(Expo + TypeScript) 위에서, 우리가 가진 자산(`spec/`의 기도 규칙과 v5의 화면 값)이 실제로 코드로 서고 실제로 화면에 뜨는가?"**

그래서 화면은 **로그인 한 장만** 만든다. 열 장을 다 만들면 M0가 M1·M2를 삼켜 버리고, 바닥이 틀렸다는 것을 열 장을 만든 뒤에 알게 된다. 한 장이면 바닥의 모든 층이 한 번씩은 관통된다 — 성화 슬롯 표(로그인 340px 띠), 디자인 토큰(색·서체), 폰트 번들, 화면 레이아웃, 웹 빌드, 스크린샷 검증까지.

아홉 화면의 자리는 이렇다. 기도와 하루 완주는 M1, 홈·새 기도·여정 상세·여정 완주·설정 다섯은 M2, 초대 코드 입력과 함께 바치기 배정 둘은 M3다(`docs/plan/development-plan.md` §6-3).

## 3. 만들 것 일곱

### 3-1. Expo + TypeScript 프로젝트 골격 — 저장소 루트에 앉힌다

**폴더 구조는 정해져 있다**(`decisions.md` Q-15). 루트에는 이미 `docs/`·`spec/`·`.claude/`·`.github/`가 있고, 앱은 그것들과 공존해야 한다.

```
/                       ← 저장소 루트 = Expo 프로젝트 루트
├─ package.json         ← 루트에 둔다
├─ app.json  eas.json   ← 3-6
├─ tsconfig.json
├─ app/                 ← 화면과 라우팅 (M0에서는 로그인 한 장)
├─ src/
│  ├─ domain/           ← 3-2 기도 도메인 상수 (spec/ 을 import)
│  ├─ theme/            ← 3-3 디자인 토큰
│  └─ art/              ← 3-4 성화 슬롯 표와 뽑기 함수
├─ assets/
│  ├─ art/              ← 성화 16장 (3-4에서 복사)
│  └─ fonts/            ← Noto Serif KR · Noto Sans KR
├─ docs/  spec/  .claude/  .github/   ← 기존 그대로
```

왜 루트인가. Expo 도구 사슬(`expo` CLI와 EAS Build)이 저장소 루트를 프로젝트 루트로 가정할 때 설정이 가장 적다. 하위 폴더에 넣으면 CI와 EAS 양쪽에 작업 폴더 설정을 따로 얹어야 하고, 그 설정이 어긋나면 "로컬은 되는데 클라우드 빌드만 실패"하는 형태로 나타난다.

**함께 할 것.** `.gitignore`에 `.expo/`·`dist/`·`web-build/`·`ios/`·`android/`를 더한다(`node_modules/`는 이미 있다). 저장소에 이미 있는 파일을 지우거나 옮기지 않는다.

### 3-2. `spec/`의 JSON을 읽어 쓰는 도메인 상수와 단위 테스트

**`spec/`을 복사하지 말고 import 한다.** 복사하면 두 벌이 생기고, 기도 규칙이 바뀌었을 때 어느 쪽이 정본인지 화면만 보고는 알 수 없게 된다. `spec/`은 프레임워크와 무관한 도메인 정본으로 만들어 둔 폴더이며, 그것이 그 폴더의 존재 이유다(`spec/README.md`).

TypeScript에서 JSON을 import 하려면 `tsconfig.json`에 `resolveJsonModule`이 필요하고, 루트 밖이 아니라 루트 안이므로 경로는 그대로 닿는다. JSON에는 타입이 없으므로 **`src/domain/`에 타입 정의를 두고 import한 JSON을 그 타입으로 좁혀 쓴다** — 그래야 오타가 타입 검사에서 잡힌다.

단위 테스트로 아래 넷을 확인한다. 값의 출처를 함께 적었으니 테스트가 무엇을 지키는지 분명히 해 두라.

| 무엇을 확인하나 | 통과 기준 | 출처 |
|---|---|---|
| **77단계 시퀀스의 길이와 구성** | `steps` 배열의 길이가 정확히 77. 시작 기도 구간이 7단계이고 그 구성이 성호경·사도신경·주님의 기도·성모송 셋·영광송 순서다. 나머지가 14단계짜리 단 다섯으로 나뉘고, 각 단이 신비 선포·주님의 기도·성모송 열·영광송·구원을 비는 기도로 이뤄진다. `index`가 0부터 76까지 빠짐없이 이어진다 | `spec/prayer-sequence.json` · PRD §1-3 · FR-10 |
| **54일 여정의 청원과 감사 구분, 그리고 신비 순환** | 며칠째가 1~27이면 청원, 28~54면 감사. 오늘의 신비는 `cycle[(dayIndex - 1) % 3]`이고 순환은 환희·고통·영광 셋이다(**빛의 신비는 54일 기도에 들어가지 않는다** — 경계값 1·3·4·27·28·54를 반드시 테스트에 넣어라) | `spec/mysteries.json`의 `rules.fiftyfour` · `spec/journey-rules.md` §1 · FR-43 |
| **요일 규칙 (FR-43)** | 날마다 기도와 9일 기도는 요일로 신비를 정한다. 인덱스 0이 일요일이며 순서는 영광·환희·고통·영광·빛·고통·환희다. **54일 기도에는 이 규칙을 적용하지 않는다**는 것까지 테스트한다 | `spec/mysteries.json`의 `rules.weekday` |
| **받는 사이 공식** | `(900ms + 사용자 몫 글자수 × 132ms) ÷ 속도계수`. 속도계수는 느리게 0.75 · 보통 1 · 빠르게 1.35. 신비 선포 뒤는 이 공식이 아니라 **고정 2200ms**다. 사용자 몫 글자수는 낭송 방식에 따라 다르다 — 교대는 뒷 절 글자수, 전부 소리로는 0, 읽지 않기는 앞 절과 뒷 절을 합한 글자수 | `spec/journey-rules.md` §4 · 06-d 화면 B 비화면 채널 · FR-07 |

**M0에서 만드는 것은 계산 함수까지이고, 이것을 화면에 붙이는 것은 M1이다.** 지금은 함수와 테스트만 있으면 된다.

### 3-3. 디자인 토큰 — v5 낮 벌의 값을 그대로

**값의 출처는 `docs/design/v5/index.html` 하나다. 눈으로 보고 옮기지 말고 파일에서 값을 그대로 가져와라.** v5는 색·글자 크기·간격을 스타일시트에 한 줄도 두지 않았고 전부 각 화면의 인라인 스타일에 글자 그대로 박아 두었다(`docs/design/v5/README.md`). 그래서 값을 찾는 일은 해당 화면의 마크업을 읽는 일이다.

M0에서 토큰으로 뽑을 것은 **낮 벌의 색과 서체 계단**이다. 로그인 화면 한 장에서 이미 아래가 전부 나온다.

- 색: 먹빛 본문 `#1F2530`, 회색 보조 `#5C6272`, 반전 글자 `#F5F1E6`, 괘선 `rgba(31,37,48,.16)`, 단추 테두리 `rgba(31,37,48,.30)`.
- 서체 계단: `Noto Serif KR` 400/38px(제목) 과 `Noto Sans KR` 400·500의 10.5 · 11 · 12.5 · 13.5 · 15px, 각 크기에 붙은 줄 높이와 자간(`letter-spacing:.24em` 같은 값)까지 함께 옮긴다.
- 터치 높이 80px(v5의 실제 값). 팀이 Q-06b에서 88px를 기본값으로 잡았으나 **v5가 80px로 그렸으므로 M0는 v5를 따르고**, 두 값의 차이는 M2의 검수에서 KimDesigner와 정한다. 지금 임의로 바꾸지 마라.

**폰트는 번들로 넣는다.** v5는 구글 폰트를 웹에서 불러오지만, 앱은 네트워크 없이도 같은 글꼴로 떠야 하므로 `assets/fonts/`에 파일로 넣고 Expo의 폰트 로딩으로 붙인다.

**밤 벌은 M0에서 만들지 않는다.** v5에 밤 벌이 없기 때문이며, 처리 방침은 `decisions.md` Q-14가 정했다(M2에서 파생). 다만 **토큰 구조는 두 벌을 나중에 받을 수 있는 모양으로** 잡아라 — 색을 화면에 직접 쓰지 말고 토큰 이름으로 쓰라는 뜻이다.

### 3-4. 성화 슬롯 표와 뽑기 함수 — 인계에서 가장 값진 자산

`docs/design/v5/index.html`의 **`ART` 배열**(파일 343행 부근)을 코드 데이터로 옮긴다. 그림 16장 각각이 네 슬롯에 대한 초점 좌표를 따로 가지며, 어느 초점으로도 이목구비가 들어오지 않는 그림은 그 슬롯의 `no` 목록에 적혀 있다.

| 슬롯 이름 | 어디에 쓰이나 | 기하 |
|---|---|---|
| `login` | 로그인 화면 위쪽 띠 | 390 × 340 |
| `thumb` | 홈 카드의 썸네일 | 96 × 124 |
| `prayer` | 기도 화면 배경 | 390 × 148 |
| `finish` | 완주 화면 띠 | 390 × 248 |

이 표가 왜 값진지 적어 둔다. 같은 그림이라도 띠의 세로 비율이 달라지면 얼굴이 걸리는 자리가 달라지고, 묵주 알이 인물의 이목구비를 가리면 FR-23 위반이다. v5는 16장을 네 기하에 실제로 넣어 렌더하고 눈으로 보며 좌표를 하나씩 정했다. **그 노동의 결과가 이 배열이므로 값을 다시 정하지 말고 그대로 옮긴다.** 현재 `no` 목록에 걸린 것은 셋이다 — `06_Side_Jesus`·`11_Mary_Rosary_White_Gold`·`12_Mary_Child_Neutral`이 모두 `prayer` 슬롯에서 빠진다.

**그림 파일 16장을 `docs/design/v5/art/`에서 `assets/art/`로 복사한다.** 여기서만은 복사가 맞다 — 앱 번들에 들어가야 하는 자산이고, `docs/`는 문서 폴더라 번들 대상이 아니기 때문이다. 파일 이름은 `ART` 배열의 `f` 값과 정확히 같아야 하므로 바꾸지 마라. (참고: 파일 번호에 `09`가 없다. 워터마크 때문에 v5가 풀에서 뺀 것이며 결함이 아니다.)

**뽑기 규칙을 함수로 만들고 단위 테스트를 붙인다.** 규칙은 셋이다.

1. **한 세션 안에서 그림이 고정된다.** 화면을 오갈 때마다 성화가 바뀌면 여정의 정체성이 깨진다. 앱을 열 때 한 번 섞고 그 순서를 세션 내내 쓴다.
2. **비복원 추출이다.** 이미 쓴 그림은 다시 집지 않아, 한 화면 안에서 같은 그림이 겹치지 않는다.
3. **`no` 슬롯은 제외한다.** 그리고 **여정용 그림은 세 슬롯(`thumb`·`prayer`·`finish`)을 모두 통과해야 한다** — 홈에서 본 그림이 그 여정의 기도와 완주에서도 같은 그림으로 이어져야 하기 때문이다.

테스트에서 확인할 것: 여정용으로 뽑힌 그림이 세 슬롯 어디에서도 `no`에 걸리지 않는다 · 같은 세션에서 두 번 뽑으면 같은 결과가 나온다 · 연달아 뽑으면 서로 다른 그림이 나온다 · 풀이 바닥나는 경우에 함수가 터지지 않는다.

**섞기에 난수를 쓰므로 테스트에서는 씨앗을 주입할 수 있게 만들어라.** v5는 진단용으로 `?art=01,02,07` 질의 문자열 손잡이를 두었는데, 같은 목적의 손잡이를 함수 인자로 두면 테스트가 결정적으로 돈다.

### 3-5. CI 검사 하나 — 타입 검사·테스트·웹 빌드

`.github/workflows/`에 새 워크플로 파일 하나를 만든다. **이 폴더는 창고 동기화 봇이 내려보내지 않으므로 이 저장소에서 만드는 것이 맞다**(원본 우선 규칙의 예외 항목). 이미 있는 여섯(`asset-graph` · `branch-overlap` · `file-registry` · `integration-board` · `pr-gate-check` · `sync-skills`)을 건드리지 말고 하나를 더한다.

이 검사가 하는 일은 셋이다 — 의존성 설치, 타입 검사와 단위 테스트, 그리고 **웹 빌드 성공 확인**. 웹 빌드를 CI에 넣는 이유는 타입 검사와 테스트가 통과해도 번들이 깨지는 경우가 있기 때문이고, 이 저장소에서 웹 빌드는 검증의 유일한 통로라 깨지면 즉시 알아야 한다.

### 3-6. `app.json`과 `eas.json` — 갖추되 실행하지 않는다

앱 이름(한국어 표시 이름 "묵주"), 번들 식별자와 패키지 이름, 아이콘과 스플래시 자리, 지원 방향(세로 고정), 그리고 EAS 빌드 프로필 셋(개발·내부 배포·스토어 제출)을 적는다.

**계정이 없어 실행할 수 없으므로, 실행하지 않았다는 사실을 README에 명시한다.** "계정 연결 뒤 실행"이라는 말이 저장소 안에 남아 있어야, 다음 세션이 이 설정을 "이미 돌려 본 것"으로 오해하지 않는다. 검증되지 않은 설정을 검증된 것처럼 두는 것이 이 단계에서 가장 하기 쉬운 거짓말이다.

### 3-7. 화면 한 장 — 로그인(`s-login`)

`docs/design/v5/index.html`의 `<div class="scr" id="s-login">` 블록을 값 그대로 React Native로 옮긴다. 그 블록 안에 이미 값이 전부 있다 — 340px 성화 띠와 그 초점 좌표, 여백 `34px 24px 0`, 자간 `.24em`의 10.5px 라벨 "54일 기도", 38px 명조 제목 "묵주", 13.5px 본문 두 줄, 80px 높이의 단추 셋(구글·애플·초대 코드), 11px 각주 두 줄.

**한 곳만 v5와 다르게 만든다.** 세 번째 줄 `초대 코드로 들어가기`(v5의 `go-invite1`)를 **넣지 않는다.** 결정 1-1이 "계정이 필수라 로그인 전 합류는 성립하지 않으므로 로그인 화면의 진입점은 뺀다"고 정했고, v5에는 그 줄이 아직 남아 있어 둘이 어긋난다. 이 충돌은 `decisions.md` Q-13이 판정했다 — **결정 1-1이 이긴다.** 결정 2가 v5에 준 권한은 화면의 모양·문구·값에 대한 정본 자격이지, 이미 내린 동작 결정을 뒤집는 권한이 아니기 때문이다. 나머지 값은 v5 그대로 두고, 그 줄이 차지하던 80px만큼 아래 여백을 늘린다.

**로그인 단추는 M0에서 눌러도 아무 일이 일어나지 않는다.** 실제 인증은 M3에서 Supabase를 붙이며 만든다. 지금 가짜 동작을 넣지 마라 — 눌리는데 아무 일도 안 일어나는 단추가, 눌리면 거짓 화면으로 넘어가는 단추보다 정직하다.

## 4. 무엇이 통과인가 — M0 작업완료의 조건 다섯

아래 다섯을 모두 만족해야 **작업완료**다. 하나라도 못 하면 작업완료라고 부르지 않는다(communication 규칙 7-1).

| # | 조건 | 어떻게 증명하나 |
|---|---|---|
| 1 | **타입 검사 통과** | 명령과 그 출력 |
| 2 | **단위 테스트 통과** | 통과한 테스트 수와 그 목록 — 3-2의 넷과 3-4의 뽑기 규칙이 포함돼야 한다 |
| 3 | **웹 빌드 성공** | `expo export --platform web`의 성공 출력 |
| 4 | **그 빌드를 띄워 로그인 화면 스크린샷 한 장** | 실제로 뜬 화면. 성화 띠·제목·단추 둘이 보여야 한다. `webapp-testing` 스킬의 Playwright를 쓴다 |
| 5 | **콘솔 오류 0건** | 같은 세션의 브라우저 콘솔 출력. 경고는 남겨도 되지만 오류는 0이어야 한다 |

**보고에 "보는 법" 세 줄을 넣는다**(communication 규칙 7-4). 로그인 화면은 새 진입점이므로 이 세 줄이 필요하다 — 어디서(웹 빌드를 띄운 주소), 무엇을 하면(열면 바로), 무엇이 보이나(성화 띠 아래 "묵주" 제목과 로그인 단추 둘).

**그리고 못 한 것을 정직하게 적는다.** §7이 그 목록이다.

## 5. 지킬 것과 하지 말 것

- **`spec/`을 복사하지 않는다.** import 한다(3-2).
- **v5의 값을 눈으로 옮기지 않는다.** 파일에서 그대로 가져온다(3-3·3-4·3-7).
- **화면을 더 만들지 않는다.** 로그인 한 장이다. 아홉 장은 M1·M2·M3의 일이며, 지금 만들면 어느 마일스톤이 무엇을 증명했는지가 섞인다.
- **`.claude/` 아래를 고치지 않는다.** 그 원본은 창고(Template-repository)이고 동기화 봇이 내려보낸다(원본 우선 규칙). 고칠 거리를 발견하면 `docs/lessons.md`에 세 줄로 적고 하던 일을 계속한다(교훈 백포트 규칙).
- **`docs/design/v5/`를 고치지 않는다.** 시안 정본이다. 값이 이상해 보이면 고치지 말고 보고에 올린다.
- **되돌리기 어려운 것과 바깥으로 나가는 것은 먼저 묻는다.** 유료 서비스 가입, 계정 생성, main 머지, 외부 전송이 여기 해당한다(에스컬레이션 §2).
- **`superpower` 스킬로 스펙과 계획과 테스트를 먼저 쓴다.** 계획 §10이 이미 그렇게 정해 두었다.

## 8. 사람 몫 — 공방장께 드리는 부탁 셋

아래 셋은 **사람만 할 수 있는 것**이다(계정 생성과 결제). 기계로 대신할 방법이 없어 부탁으로 올린다(communication 규칙 8-1·8-2). 셋 다 브라우저만으로 되고, 승인에 며칠 걸리는 것이 있어 **M0와 병행해 시작하시는 편이 좋다.**

### 부탁 1 — Expo 계정 (무료, 3분)

- **어디서**: 브라우저에서 `expo.dev` 접속 후 우측 상단 Sign Up.
- **무엇을**: 이메일로 계정을 만들고, 로그인한 뒤 좌측 상단의 조직(Account) 이름을 알려 주십시오. 그 이름 한 줄이면 저희가 `app.json`·`eas.json`을 연결합니다.
- **성공하면 무엇이 보이나**: 로그인 후 대시보드에 Projects 목록(처음에는 비어 있음)이 뜹니다.
- **안 하면 무엇이 걸리나**: **클라우드 빌드를 한 번도 돌릴 수 없습니다.** iOS·Android 앱 파일이 나오지 않으므로 M4의 검증 배포가 통째로 막힙니다. 비용은 들지 않습니다(무료 구간 월 30회).

### 부탁 2 — Apple Developer Program 등록 (연 $99, 승인에 며칠)

- **어디서**: 브라우저에서 `developer.apple.com/programs` 에 접속해 Enroll 을 누릅니다. Apple ID로 로그인합니다.
- **무엇을**: 개인 자격으로 등록하고 연회비 $99를 결제합니다. 애플의 신원 확인 절차가 있어 **승인까지 보통 며칠 걸립니다.**
- **성공하면 무엇이 보이나**: `appstoreconnect.apple.com`에 들어가 My Apps 화면이 열립니다(처음에는 앱이 없음).
- **안 하면 무엇이 걸리나**: **iOS 앱을 만들 수도 배포할 수도 없습니다.** TestFlight(출시 전 테스트 배포 통로)도 이 등록 위에서만 동작하므로, 공방장 폰에서 앱을 열어 보는 일 자체가 불가능합니다. 이것이 M1의 실기기 확인을 막는 유일한 요인입니다.

### 부탁 3 — Google Play Console 등록 (1회 $25, 승인에 며칠)

- **어디서**: 브라우저에서 `play.google.com/console` 에 접속해 "개발자 계정 만들기"를 누릅니다. 구글 계정으로 로그인합니다.
- **무엇을**: 개인 개발자로 등록하고 등록비 $25(1회)를 결제합니다. 구글도 신원 확인을 하며 **며칠 걸립니다.**
- **성공하면 무엇이 보이나**: Play Console 대시보드에 "앱 만들기" 버튼이 있는 화면이 열립니다.
- **안 하면 무엇이 걸리나**: **Android 배포가 막힙니다.** 결정 0-3으로 Android가 V1 범위에 들어와 있으므로, 이것이 없으면 V1의 절반이 나가지 못합니다. 다만 iOS와 달리 M1의 실기기 확인은 막지 않습니다.

**세 부탁의 우선순위.** 부탁 1을 가장 먼저 하시고, 그다음이 부탁 2, 마지막이 부탁 3입니다. 부탁 1은 무료이고 즉시 끝나며 다른 둘의 전제입니다. 부탁 2는 승인이 오래 걸리는 데다 M1의 실기기 확인을 막고 있어 그다음입니다. 부탁 3은 M4의 Android 배포 전까지만 되면 됩니다.
